# Enterprise Intelligence & Decision Platform (EIDP) — the Organizational Brain

**Status:** Living engineering specification. Permanent source of truth for the EIDP
program. Update the Implementation Tracker, DDRs, and Changelog with every change.

**Owner:** Vrittih / EduRankAI platform.
**Last updated:** 2026-08-03.

---

## 0. Mission

Transform the operational data already generated by every platform (Recruitment OS,
Workforce OS, AIOS, Self-Evolving Intelligence, ICAE, Communication, Knowledge,
Identity) into **strategic intelligence**. Not another dashboard — an organizational
brain that measures health, forecasts, and generates explained decision support so
every decision, from founder to intern, becomes data-informed.

Hard constraints (inherited): **fully in-house** (no external LLM/ML/vector DB —
deterministic, explainable models only), **capability-driven** authorization (never
role), **CHF** pricing basis, honesty (surface evidence and confidence; never fabricate),
no emojis (own SVG icons).

## 1. Architecture

EIDP is a **read-mostly intelligence layer** over the existing operational stores. It
computes, it does not own primary data. Three pure engines + an aggregation/API layer
+ a capability-gated Executive Workspace.

```

                 └───────────────────────┬───────────────────────┘

        ▼                                ▼                                  ▼
  Health engine                   Decision engine                   Forecast engine
  lib/intelligence/               lib/intelligence/                 lib/intelligence/
  - health.ts (metric extraction  - decisions.ts (rules →           - forecast.ts (OLS
    from DB → DomainHealth via      DecisionCards w/ evidence,        regression, MA,
    score.ts)                       confidence, alternatives,         method-selecting
  - score.ts (normalize/roll-up)    risks; generic + domain rules)    forecaster, bucketing)
        └────────────────────────────────┼────────────────────────────────┘
                                         ▼
                     Reused primitives (NOT duplicated)
   AIOS execute/recommend/reason · Recommendation(+Feedback) · capability framework
```

**Design rules:**
- EIDP reads operational tables and derives; it introduces **no** new primary-data
  models in v1 (metrics are computed on demand, optionally snapshotted later).
- Scoring/forecasting/decisions are **pure functions** (unit-tested in isolation); the
  API layer is the only part that touches the DB.
- Capability-gated on `intelligence.view` (and finer per-domain caps), derived for
  founders/CXOs/admins — never a role check.

## 2. Decision Models

A **DecisionCard** (`lib/intelligence/decisions.ts`) is the atomic unit of decision
support and always carries the spec-mandated explanation:

```ts
interface DecisionCard {
  id; domain; title
  severity: "critical" | "high" | "medium" | "low" | "opportunity"
  recommendation: string
  evidence: string[]                 // the facts behind it
  supportingMetrics: { label; value; band }[]
  confidence: number                 // 0..1, from data coverage / fit quality
  alternatives: string[]             // other courses of action
  risks: string[]                    // what could go wrong / caveats
}
```

Rules are `(ctx: { domains, forecasts }) => DecisionCard[]`. Generic rules
(shipped): poor-domain-health → card; falling forecast → early-warning; rising
forecast → growth opportunity. Domain rules (retention risk, skill shortage, hiring
demand, promotion readiness, budget priority) are registered by the API once real
metrics are extracted (health engine). Cards are deduped by id and ranked severity →
confidence. Cross-card ordering may defer to `lib/aios/recommend.rank`.

## 3. Business Intelligence — the metric catalog

The **Organizational Health Engine** (`health.ts`) computes, per domain, a set of
`MetricSpec`s (value + good/bad band + direction + weight) and rolls them up via
`score.ts` into a domain score and an overall org-health index. Metrics are computed
only where real data exists; anything unmeasurable is declared in Known Gaps (never
faked). The domain catalog (populated concretely once the health engine lands):

- **Executive** — org growth, overall health index, coverage.
- **Recruitment** — hiring velocity, time-to-hire, offer acceptance, candidate quality,
  interview quality, funnel conversion.
- **Workforce** — internship completion, PPO conversion, task/project health, stipend spend,
  engagement proxy.
- **Learning** — completion rate, certificate issuance, assessment pass rate, roadmap velocity.
- **Research / Project** — project health, research productivity (where modelled).
- **Financial** — revenue proxy (paid × plan CHF), conversion rate, trial conversion, plan mix.
- **Community** — activity, message volume, network growth, notification engagement.
- **Security / Compliance** — 2FA adoption, ID-verification rate, audit-action volume,
  partner/company approval compliance.
- **AI / Knowledge** — AI adoption/utilization (AiRun volume + unique subjects),
  recommendation acceptance, knowledge growth (SemanticDoc/MemoryEntry over time), self-eval health.
- **Operational / Infrastructure / Developer / Product** — as data permits (see Gaps).

## 4. AI Intelligence

Reuses AIOS (`lib/aios/*`): the decision engine speaks the same evidence+confidence
vocabulary as `reason`/`recommend`; cross-card ranking can call `recommend.rank`;
adoption metrics read `AiRun`/`PlatformEvent`; recommendation quality reads
`RecommendationFeedback`. EIDP registers no competing intelligence — it aggregates.

---

## 5. Executive Intelligence

The **Executive Workspace** (`/executive`, capability-gated) surfaces: Organization
Overview (org-health index + band), Strategic KPIs (top metric per domain), Critical
Alerts (Critical/At-risk domains), Top Risks (negative-trend + critical decision cards),
Growth Opportunities (opportunity cards), Decision Queue (ranked DecisionCards),
Forecasts (per key series), AI Insights, Cross-platform Intelligence. Capability-driven:
a Department Head sees their domains; a founder sees all.

---

## 6. Operational & Predictive Intelligence

- **Operational**: current-state health per domain, refreshed on load (bounded queries).
- **Predictive** (`forecast.ts`): each key series (e.g. `Application.appliedAt`,
  `User.createdAt`, `Interview.scheduledAt`, `AiRun.createdAt`) is bucketed into equal
  windows and forecast a short horizon with an honest confidence. Method is chosen
  deterministically (linear when a real trend fits, else moving average, else naive).

## 10. Design Decision Records

- **DDR-1: Read-mostly, no new primary models (v1).** Metrics are derived on demand;
  optional snapshotting is a later increment. Avoids migration + staleness.
- **DDR-2: Pure engines, DB only at the edge.** Scoring/forecast/decision math is
  unit-tested in isolation; only the API layer queries Prisma.
- **DDR-3: Honesty over completeness.** Unmeasurable metrics are `null` (excluded from
  scores, shown as "no data"), never estimated. Gaps are documented.
- **DDR-4: Capability-gated, per-domain.** `intelligence.view` plus finer caps; a
  manager sees their domains, a founder sees all. Never a role check.
- **DDR-5: Reuse the cognitive layer.** Decisions reuse AIOS evidence/confidence
  vocabulary and may defer ranking to `recommend.rank`; no competing engine.

## 11. Verification

- **Unit** (done for #2–#4): regression correctness (perfect line R²=1, flat, single
  point), forecaster method selection + clamping + confidence, metric normalization
  (both directions, clamping, null handling), domain roll-up skipping nulls, decision
  ranking/dedup/explanation-completeness.
- **Integration** (pending): APIs return correct shapes; capability gating denies the
  unentitled; queries are bounded.
- **Adversarial** (pending, #10): a review workflow verifies correctness, explainability,
  security (no cross-tenant leak), capability gating, performance.

## 12. Roadmap

1. **v1 (this program):** engines (✅) + health extraction + APIs + capability +
   Executive Workspace + adversarial review.
2. **v1.1:** snapshot health/metrics to a time-series table for real historical
   forecasting (vs on-the-fly bucketing); scheduled digest to executives.
3. **v1.2:** per-domain workspaces (Recruitment/Workforce/Finance heads); configurable
   KPI selection; alert thresholds.
4. **v2:** anomaly detection on series; what-if decision simulation.

## 13. Migration Notes

v1 adds **no** schema changes. v1.1 would add a `MetricSnapshot` model (append-only,
`{ domain, key, value, capturedAt }`) via the standard dual-DB push dance (sqlite local,
Postgres prod). Capability additions are code-only (`lib/capability/catalog` + derive).
